# Kicad-ng: графовая модель истории проектирования

Черновик v0.9, 2026-10-11. Формальная модель истории как графа состояний и операций
с несколькими измерениями, веером недетерминированных исходов и пере-решаемыми
слияниями. Проверена на трёх сценариях в конце.

Происхождение: принципы TTD v2 из unreal-ng (exact-or-report, cost follows change,
piece store с шарингом, журнал входов + материализация) — обобщённые с плоской памяти
одной машины на граф объектов с несколькими осями.

---

## 1. Примитивы

### 1.1 Состояние `S`

Неизменяемое, контент-адресуемое. Merkle-дерево:

```
S = hash( domain → ( identity → hash(canon(object)) ) )
```

- **Домены**: `schematic`, `layout`, `rules`, `library-pins`, `variants`, `meta`.
- **Каноникализация `canon`** — своя на домен; определяет класс эквивалентности,
  в котором два объекта считаются одним состоянием. Координаты в целых нм (как в
  KiCad) каноничны сами по себе; порядок вершин полигона, порядок элементов в
  списках, имена нетов (см. identity) — нормализуются. Геометрическая эквивалентность
  «с точностью до допуска» **не** делается квантованием (краевые эффекты), а
  выносится в derived-сравнение (§4): два состояния с разным хэшем могут быть
  объявлены эквивалентными *запросом*, но не *хранилищем*.
- Хранение — piece store по `(domain, identity)` с refcount и шарингом между
  состояниями; два состояния с одним хэшем — один узел графа (решётка).

### 1.2 Идентичность `I`

Идентичность объекта **не** случайный UUID при создании, а

```
I = (op_id, ordinal)
```

где `op_id` — id операции, которая объект создала (§1.3), `ordinal` — порядковый
номер внутри неё. Следствие: одна и та же операция, переигранная в другой ветке,
создаёт **те же** идентичности → ветки, сделавшие одно и то же, сходятся сами.

Неты, пины, футпринты, треки, зоны, правила, листы — всё по этой схеме. Имя нета —
атрибут, а не идентичность; переименование не ломает ссылок.

### 1.3 Операция `O`

```
O = {
  op_id:      (author, hybrid_logical_clock)   -- не зависит от базы
  intent:     verb + refs(I...) + params        -- семантика, что хотели
  reads:      footprint                         -- что читала
  writes:     footprint                         -- что меняла
  result:     { I → (hash_before, hash_after) } -- фактическая дельта
  class:      D | N | X
  generator:  { algo, version, seed }           -- для N и D
  parent_op:  op_id | null                      -- причинность (кто породил)
}
```

**Классы детерминизма:**
- `D` — детерминирована относительно `reads`: тот же вход → тот же результат.
  Переигрывается заново на изменённой базе, результат сравнивается со старым.
- `N` — недетерминирована (push-and-shove, автоплейс, LLM-агент). Порождает **веер**.
- `X` — внешняя: ручная правка, импорт. Переиграть нельзя, только применить
  результат; на конфликте — человек.

**Footprint** (область чтения/записи) = множество идентичностей ∪ множество
пространственных ячеек `(layer, cell)` на сетке. Пространственная часть нужна,
потому что геометрическое взаимодействие (clearance) не выражается через
идентичности.

`op_id` намеренно не включает хэш базового состояния — иначе rebase менял бы id,
а с ним и идентичности созданных объектов.

### 1.4 Узлы графа

| Узел | Что это | Входы | Выходы |
|---|---|---|---|
| `State` | §1.1 | — | — |
| `Op` | применение операции | 1 State | 1 State (D, X) |
| `Fan` | операция класса N | 1 State | k State (альтернативы), k ≥ 1 |
| `Join` | выбор/слияние | k State | 1 State |

`Join` — сам по себе операция класса `D` с

```
Join = {
  criterion:   выражение над derived (§4) и/или {human: who, saw: hash(view)}
  selected:    индекс выбранного ребёнка
  mode:        select | merge
}
```

- `select` — один из детей веера.
- `merge` — объединение дельт независимых веток (§3.3).

Проигравшие дети **не удаляются**: они остаются достижимы из `Fan`, собираются GC
только по явному бюджету, причём `Join` с критерием и оценками детей сохраняется
всегда (это данные).

### 1.5 Рёбра = измерения

| Измерение | Ребро | Смысл |
|---|---|---|
| **Time** | `State → Op → State` | порядок применения (то, что сейчас undo) |
| **Alt** | `Fan → State×k`, `State×k → Join` | альтернативные исходы |
| **Derive** | `State.domain → Derived` | деривация (§4), с memo по хэшу входов |
| **Variant** | `State ↔ State` | параллельно живущие конфигурации (BOM-варианты, stackup) |
| **Cause** | `Op → Op` | `parent_op`: что породило (UI-действие → переаннотация → …) |

Авторство — атрибут `Op`, не ребро.

**Позиция** = путь в графе, а не скаляр:

```
Position = { time: op_id, choices: { fan_id → child }, variant: variant_id, asof: hlc }
```

`asof` — битемпоральность: «как выглядело решение на момент T» отдельно от «какое
состояние на шаге N».

## 2. Линеаризация — это проекция

История как список = **представление** графа под политикой:

```
linearize(root, policy) :
  идти по Time-рёбрам;
  в Fan — взять ребёнка, выбранного его Join (или policy.choices);
  в Join(merge) — порядок дельт по policy.order (детерминированный);
  Variant — зафиксирован policy.variant.
```

Undo/redo, scrubbing, blame, bisect — всё операции над одной линеаризацией.
Другая политика (другой вариант, «as of вчера», «если бы в Fan#120 выбрали C») —
другая линия над тем же графом, без копирования.

## 3. Коммутация и rebase

### 3.1 Коммутация

`a` и `b` коммутируют ⇔

```
writes(a) ∩ (reads(b) ∪ writes(b)) = ∅  и  writes(b) ∩ (reads(a) ∪ writes(a)) = ∅
```

Footprint включает пространственные ячейки, поэтому два трека в одном месте разных
нетов **не** коммутируют (clearance), а в разных углах платы — коммутируют, даже
если оба читают `rules`. Derived в footprint не входит — он пересчитывается.

### 3.2 Rebase хвоста на изменённую базу

Для каждой `op` хвоста по порядку:

1. **Коммутирует** с изменением базы → применить `result` как есть (replay-by-result).
2. **Не коммутирует, класс D** → выполнить `intent` на новой базе; сравнить с
   `result`; при расхождении — операция помечена `diverged`, diff в отчёт.
3. **Не коммутирует, класс N** → заново `Fan` с тем же `generator`; `Join`
   переоценивается по сохранённому критерию (§3.4).
4. **Не коммутирует, класс X** → конфликт; операция помечена `blocked`,
   хвост после неё не применяется, пока человек не разрешит.

Принцип TTD «exact или отчёт»: rebase либо точен, либо называет каждую операцию,
которая разошлась, и чем.

### 3.3 Merge независимых веток

Две ветки от общей базы: дельты `Δa`, `Δb`.

- Все операции попарно коммутируют → `Join(merge)` применяет обе дельты;
  derived (DRC и т. д.) пересчитывается на результате.
- Есть некоммутирующие пары → **конфликт становится веером**: `Fan` с детьми
  `rebase(b на a)`, `rebase(a на b)` (и, при желании, перегенерация N-операций
  на объединённой базе), затем `Join(select)` по критерию. Конфликт слияния —
  обычный узел графа, а не модальное окно.

### 3.4 Пере-решение

`Join.criterion` читает derived. Derived memoизирован по хэшу входов (§4). Когда
меняется что-то во входах критерия (правило, stackup, библиотека) — derived
инвалидируется, `Join` получает статус `stale`.

Политика:
1. Переоценить критерий на **существующих** детях. Если выбор не изменился —
   `Join` снова `fresh`, хвост не трогается.
2. Если выбор изменился — выбрать нового ребёнка, rebase хвоста (§3.2) от
   `Join` с дельтой `old_child → new_child`.
3. Если **ни один** ребёнок не проходит — предложить re-fan (перегенерация с тем
   же `generator` на той же базе с новыми правилами). Автоматически — только в
   рамках бюджета.
4. Критерий с `human` → `stale` не разрешается автоматически; человеку
   показывается, что изменилось во входах с момента, когда он решал
   (`saw: hash(view)` против текущего).

## 4. Derived-слой

Всё, что вычислимо из состояния, **не хранится в состоянии**:
netlist из схемы, connectivity, ratsnest, заливки зон, DRC/ERC, длины и skew,
импедансы, BOM, gerber.

```
derived(f, inputs_hash) → memo
```

(как Salsa/Adapton). «Change propagation» = инвалидация по Derive-рёбрам +
ленивый пересчёт. Дорогие derived (заливки) кэшируются на диск по хэшу входов —
аналог `TTDFrameCache`, не истина.

**Ключевое следствие для схемы ↔ платы:** layout-состояние — это *только*
размещение и геометрия трассировки, ссылающиеся на идентичности пинов и нетов.
Какие пины у футпринта, какой нет на паде — derived из схемы + назначения
футпринтов. Операция «Update PCB from schematic» исчезает как понятие:
изменение схемы инвалидирует derived платы, и ratsnest/DRC показывают, что
теперь не сходится.

## 5. Сценарии

### 5.1 Пере-решение после смены ограничения

- Op#120: `Fan` — автороутер, 3 варианта разводки DDR-шины (A, B, C).
  Op#121: `Join(select)`, критерий `DRC_clean ∧ min(skew)`, выбрана B.
- Ops#122–300: разводка остального, часть — рядом с DDR (не коммутирует с
  `B→C` по пространственным ячейкам), часть — в другом углу (коммутирует).
- Op#301: в `rules` меняется целевой импеданс DDR.

Что происходит:
1. `rules` ∈ inputs(DRC) → DRC-derived инвалидирован → Join#121 `stale`.
2. Переоценка на A, B, C: B теперь не `DRC_clean`, C проходит с большим skew,
   чем B раньше, но лучшим из оставшихся → selected = C.
3. Rebase #122–300 на `B→C`: коммутирующие — replay-by-result; две операции
   класса D рядом с DDR перевыполнены, одна разошлась (`diverged`, diff
   показан); одна ручная правка X рядом — `blocked`, ждёт человека.
4. Отчёт: «решение #121 пересмотрено: B→C; 2 операции переиграны, 1 разошлась,
   1 требует внимания». История линейна в проекции, граф хранит оба пути.

Без графа: пользователь вспоминает, что когда-то выбирал между вариантами, и
переразводит вручную.

### 5.2 Расхождение схемы и платы

- Схема: U1 заменён на вариант с другой распиновкой (op X, домен `schematic`).
- `pins(U1)`, `net(pad)` — derived из схемы + назначения футпринтов. Инвалидация
  по Derive → connectivity платы пересчитан → три трека ссылаются на пины,
  которые теперь на другом нете; ratsnest показывает, DRC помечает short.
- Треки не «устарели» и не требуют импорта: они просто стали *неправильными
  относительно текущей схемы*, и это видно сразу. Исправление — обычные
  операции на плате.
- Blame: `Cause`-ребро от DRC-ошибки → derived → схема-op → автор и момент.
  Provenance — обратный обход по Derive и Cause.

### 5.3 Два агента в параллельных ветках

- От S0: агент A разводит питание (ветка a), агент B — USB (ветка b). Оба — N.
- Merge: footprints по идентичностям не пересекаются; по пространственным
  ячейкам пересекаются в одном месте (A провёл шину под разъёмом USB).
- Коммутирующие пары → применяются; некоммутирующая пара → `Fan` с детьми
  `rebase(b на a)` (B перегенерирован с учётом шины A) и `rebase(a на b)`;
  `Join(select)` по критерию `DRC_clean ∧ min(total_length)`.
- Если оба проходят — выбран лучший; проигравший остаётся в графе. Если нет —
  человек, с видимыми обоими вариантами и причиной конфликта (ячейки).

## 6. Открытые вопросы (решать в ядре, не потом)

1. ~~Каноникализация на домен~~ — решено семантически, см. §8.
2. **Гранулярность пространственного footprint** — сетка слишком грубая → ложные
   конфликты, слишком мелкая → дорогой пересчёт. Вероятно, иерархическая
   (quadtree-ячейки).
3. ~~Intent для X-операций~~ — выводится из L2-канона результата, см. §8.3.
4. **Бюджеты веера и GC** — какие листья можно выбросить, что считается
   «данными» (Join + оценки — всегда).
5. ~~Human-критерии~~ — `saw` = L2-проекция релевантных нетов, см. §8.3.
7. **Placement на семантическом уровне** — есть ли у размещения настоящий L2
   или оно живёт на L1 (§8.2).
6. **Variant-измерение** — объекты, существующие только в части вариантов:
   это атрибут объекта или отдельные состояния с общими кусками? (Склоняюсь ко
   второму — piece store делает это дешёвым.)

## 7. Прецеденты

- **Pijul / Darcs** — коммутативность патчей, теория патчей.
- **Datomic, bitemporal БД** — несколько осей времени как first-class (`asof`).
- **Salsa / Adapton** — инкрементальный пересчёт derived по графу зависимостей.
- **W3C PROV** — модель деривации и provenance.
- **unreal-ng TTD v2** — exact-or-report, cost-follows-change, piece store с
  refcount, журнал входов + материализация, классы записываемых данных R/D/T/H.

Ни один из них не делает веер с записанным критерием и пере-решением — это
новая часть.

## 8. Семантическая каноникализация (v0.2)

Решение открытого вопроса 1, и заодно 3 и 5. Каноническая форма объекта — не
нормализованные байты, а его **смысл**; геометрия — реализация смысла.

### 8.1 Уровни эквивалентности

Вложенная цепочка отношений эквивалентности, каждое грубее предыдущего:

| Уровень | Что равно | Пример для трека |
|---|---|---|
| L0 bytes | побайтно | как есть |
| L1 geometric | нормализованная геометрия | порядок вершин, целые нм, слитые коллинеарные сегменты |
| L2 **topological** | смысл трассы | нет, якоря (пады/via), последовательность слоёв, гомотопический класс относительно неподвижных препятствий |
| L3 connectivity | только связность | нет соединяет эти пады |

Равенство на уровне k ⇒ равенство на всех более грубых. Каждый объект несёт
вектор хэшей `(h0, h1, h2, h3)`; Merkle-корень состояния — над `h2`.

**Узел графа идентифицируется по L2.** L3 слишком груб (все разводки одного
netlist'а — одно состояние), L1 слишком тонок (решётка не сходится). L1-данные
— **реализация**, прикреплённая к L2-узлу; у одного семантического состояния
может быть несколько реализаций.

Жёсткое правило: в каноническую форму входят только **настоящие отношения
эквивалентности** (транзитивные). Гомотопический класс — да. Последовательность
слоёв — да. «Длина в пределах 5 %» — **нет** (не транзитивно); метрики — это
derived-критерии для Join, не часть канона.

### 8.2 Канон по доменам

**Schematic.** Семантика = размеченный граф: компоненты (идентичность, part,
нормализованное значение: `4k7 = 4.7k = 4700Ω`, допуск), пины, неты как классы
связности. Граф размечен идентичностями, поэтому хэш тривиален — изоморфизм
искать не нужно. Реализация: позиции символов, маршруты проводов, метки, листы.

**Rules.** Семантика = эффективная таблица ограничений `(net-class, layer) →
constraints` после раскрытия умолчаний и разрешения перекрытий. Два набора
правил с разным текстом, но одной таблицей — одно состояние. Текст правил —
реализация (как исходник для скомпилированного).

**Layout / routing.** Семантика трека = `(net, упорядоченные якоря, путь по
слоям, гомотопический класс)`. Гомотопия считается **только относительно
неподвижных препятствий** (пады, отверстия, keepout, контур) — не относительно
других нетов, иначе сдвиг чужой трассы меняет класс этой (нелокальность).
Взаимодействие нетов (clearance) — уровень реализации, проверяется DRC.
Сигнатура класса — последовательность пересечений с разрезами остова
препятствий (техника топологических роутеров: TopoR, rubber-band routing Dai).

**Layout / placement.** Семантика = `(сторона, room, класс поворота, отношения
«рядом с» по правилам — decoupling у пина)`. Координаты — реализация. Это самая
слабая часть канона; возможно, placement честно живёт на L1 с L2 = L1.

**Zones.** Семантика = `(net, слой, покрываемая область как множество ячеек
грубой сетки / room, приоритет, правила заливки)`. Заливка — derived.

### 8.3 Что это меняет в модели

- **Fan схлопывается.** k реализаций роутера с одним L2 — один дочерний узел с
  k реализациями. Join по критерию выбирает реализацию (или любая, если
  критерий безразличен). Веер засоряется только по-настоящему разными
  решениями.
- **Merge агентов на общих нетах.** Одинаковое L2 → слияние тривиально,
  берётся реализация с лучшими derived-метриками.
- **Intent для X-операций выводится из результата** (вопрос 3 закрыт).
  Нарисованный вручную трек канонизируется в `(net, A→B, слои, гомотопия)` —
  это и есть намерение, которое роутер может перереализовать на новой базе.
  Ручная работа перестаёт быть вечно `blocked`.
- **`saw` для human-критериев = L2-проекция релевантных нетов** (вопрос 5).
  `stale` только когда изменился смысл, не координаты.
- **Footprints операций — семантические**: `reads: {topology(net X), rules(X)}`,
  `writes: {route(net X)}`, плюс пространственные ячейки для реализации.
- **Валидность ≠ семантика.** Две реализации одного L2-узла могут отличаться по
  DRC. DRC — derived над реализацией; Join читает его, канон — нет.

### 8.4 Цена

- Канон на домен — версионируемый алгоритм: изменение правила канонизации
  меняет все хэши → формат версионирован с первого дня, старые уровни
  пересчитываются миграцией.
- Гомотопическая сигнатура требует остова препятствий; при добавлении
  препятствия (новый пад) сигнатуры соседей пересчитываются — локально, но
  не бесплатно.
- Placement на L2 — открыт.

### 8.5 Семантика зависит от класса решения: профили

Уровень L2 из §8.1 — не глобальная константа. **Что входит в смысл, определяет
класс нета/области**, и у разных классов разные свойства являются идентичностью,
а разные — метриками. Семантический **профиль** `P` назначается нету (через
net-class/rules/явно) и задаёт:

```
P = {
  identity:    какие свойства входят в отношение эквивалентности
  constraints: жёсткие предикаты (вход/не вход в допустимое множество)
  metrics:     что оптимизируется, и порядок/веса между ними
}
```

| Профиль | identity (эквивалентность) | constraints (фильтр) | metrics (Pareto) |
|---|---|---|---|
| **plain** (низкочастотная коммутация, питание без особых требований) | L3 связность + предикат «DRC пройден» | DRC | длина, число via — почти безразлично |
| **high-speed / matched** (DDR, диффпары) | L2 топология + путь по слоям + непрерывность опорного слоя + пара как единица | DRC, impedance class, match-tolerance | skew, длина, число via, crosstalk-оценка |
| **RF / СВЧ** | **геометрия на сетке разрешения фабрики**: ширина, зазор, радиусы, via-fence, подложка | DRC, импеданс ±x | потери, отражения, EMI |

Два наблюдения, которые делают это строгим:

- **Предикат — это отношение эквивалентности** (разбиение на «проходит / не
  проходит»), поэтому жёсткое ограничение можно включать в identity. Для plain-нета
  любые две DRC-чистые разводки — одно семантическое состояние. Это даёт
  огромную сходимость там, где она и должна быть.
- **Квантование к сетке фабрики — тоже отношение эквивалентности** (floor на
  сетку), в отличие от «±5 %». Для RF это честная идентичность: фабрика ниже
  своего разрешения тоже не различает. Так L_sem для RF ≈ L1 на fab-сетке, и
  это не компромисс, а определение.

Хранение: вектор стандартных уровней `(h1, h2, h3)` считается для всех объектов
всегда; профиль — **селектор** над ними плюс профильные добавки (опорный слой,
fab-сетка), считаемые лениво и версионируемые. Поэтому смена профиля нета
(«этот нет теперь high-speed») — операция в домене `rules`, которая меняет
семантические хэши нета **без** переканонизации истории: старые уровни на месте.

### 8.6 Веер как облако решений: Pareto-фронт

Для нетривиальных профилей «выбрать одного ребёнка» — неверная модель. Дети
`Fan` после фильтра по `constraints` образуют **Pareto-фронт** по `metrics`.
Хранится фронт; доминируемые дети — кандидаты на GC. `Join` — это **политика**
над фронтом: веса, лексикографический порядок или человек.

Следствие для пере-решения (§3.4): когда меняются *веса* («теперь EMI важнее
длины»), re-fan не нужен — фронт уже есть, Join просто выбирает другую точку.
Re-fan нужен только когда меняются `constraints` или `identity` (новый
импеданс, новый профиль) — фронт считался в другом допустимом множестве.

**Смешанные платы и факторизация.** Решение всей платы — не произведение
облаков всех нетов. Пространственные footprints (§1.3) дают **граф
взаимодействия** нетов; несвязанные компоненты графа — независимые веера,
композируемые свободно; связанные — один совместный веер. Это факторизация
Pareto-фронта по графу взаимодействия (как factor graph): СВЧ-тракт и
низкочастотная периферия на одной плате живут в разных веерах, пока их
footprints не пересеклись.

**Про схему в RF.** Для СВЧ граница «схема / плата» сама зависит от профиля:
паразитные параметры разводки входят в электрическую модель, то есть layout
участвует в семантике *схемы*. В модели это выражается тем, что для RF-профиля
derived-ребро идёт и в обратную сторону (layout → electrical model), и
семантическая единица — электрическая модель, у которой схема и плата — два
представления. Это отдельная глава; здесь только зафиксировано.

## 9. Метод: суперсет и абляция (v0.4)

Конструкции модели не выбираются заранее. Берётся **суперсет** всего, что
перечислено в §1–8, каждая конструкция — независимо отключаемый флаг движка.
Суперсет прогоняется по корпусу сценариев, и по измерениям решается, что
остаётся, что выключено-но-доступно (как write journal в TTD), что удаляется.

Образец — миграция TTD v1→v2 в unreal-ng: POC 011, бенчмарки BM-1…BM-9, lz4-tier
и batching отброшены по измерениям.

### 9.1 Принцип измерения

**Частота использования — вторичный сигнал.** Страховочные конструкции
(`Join` с критерием, `asof`, exact-or-report) срабатывают редко, но без них
целые классы сценариев невозможны. Основная мера — **абляция**: конструкция
выключена, корпус прогнан заново, фиксируется что сломалось и что подорожало.

На каждую конструкцию четыре числа:

| Метрика | Что измеряет | Откуда |
|---|---|---|
| **usage** | сколько раз сработала на корпусе | счётчики движка |
| **cost** | байты в хранилище, мс на операцию, мс на seek/rebase | бенчмарк, как BM-n в TTD |
| **ablation** | сценарии, ставшие невозможными (`blocked`) или дороже (×N), без неё | прогон с флагом off |
| **convergence** | сколько состояний решётка склеила благодаря ей | число узлов с/без |

Решение: `ablation` ≠ ∅ → остаётся. `ablation` = ∅ ∧ `cost` пренебрежим →
остаётся выключенной по умолчанию. `ablation` = ∅ ∧ `cost` заметен → удаляется.

### 9.4 Стенд

По образцу `tools/verification/ttd-bench` из unreal-ng:

```
bench(config: flags, scenario: C*) → report {usage[], cost[], outcome: ok | blocked | degraded(×N), converged_states}
ablation(F_i) = Σ_scenarios ( bench(all) − bench(all − F_i) )
```

Переиспользуется из TTD: byte-for-byte сравнение конфигураций, бюджеты памяти,
формат отчётов. Первая версия стенда — до первой версии движка: сценарии и
метрики фиксируются раньше, чем реализация, иначе стенд подстроится под неё.

### 9.5 Стоимость носки суперсета

Невыключенная конструкция стоит байтов и миллисекунд (вектор хэшей на объект,
фронт вместо ребёнка, Cause-рёбра). Это измеряется той же `cost`-метрикой;
при пренебрежимой стоимости конструкция остаётся в формате выключенной —
доступной без миграции, как write journal в TTD.

## 10. Тропинки: граф как темплейт решений (v0.5)

Со временем граф с `Fan`/`Join` и записанными исходами становится **деревом
поиска**: у узлов есть число посещений и оценка исхода. Протоптанная тропинка —
узел с большим числом посещений и узким разбросом; нехоженое — малое число
посещений и широкая неопределённость. Выбор между ними — explore/exploit.

### 10.1 Join как политика исследования

`Join.criterion` получает параметр исследования:

```
score(child) = value_estimate(child) + β · uncertainty(child)
```

(UCB / Thompson sampling / MCTS-подобные правила — семейство одно). `β` —
явная ручка «аппетит к риску» на проект, профиль или класс нета:
серийная плата → β ≈ 0 (идём по тропинке, средний предсказуемый результат);
R&D → β велик (ищем крупный выигрыш). `β` **никогда не ровно 0**: тропинка
протоптана не обязательно потому, что она лучше (§10.4).

### 10.2 Ключ ситуации: темплейт между платами

Тропинка на плате A переносится на плату B, только если «то же место»
распознаётся без координат. Ключ ситуации — канон задачи, не решения:

```
situation_key = canon( profile,
                       класс топологии задачи: число якорей, конфигурация
                         препятствий по L2, число слоёв,
                       constraints )
```

Темплейт = класс эквивалентности ситуаций с распределением исходов по путям.
Это третье применение L2-канона (после сходимости решётки и вывода intent).
Хранится отдельно от истории проекта — как **библиотека ситуаций**, в которую
графы проектов публикуют свои узлы; prior для нового `Fan` берётся из неё.

### 10.3 Отложенная награда и credit assignment

Метрики в `Join` — прокси. Настоящий исход (плата прошла EMC, не потребовала
respin, работает в поле, или наоборот) приходит через недели как **внешнее
событие** — X-операция `Outcome{ref: state, verdict, evidence}`. Награда
распределяется назад по `Cause`-рёбрам на `Join`-узлы, приведшие к состоянию,
с затуханием по расстоянию. Без этого темплейт учится на прокси и переобучается
на «красиво по метрикам».

### 10.4 Чего тропинка не доказывает

- Путь протоптан, потому что генератор к нему склонён или люди привыкли — не
  обязательно потому, что он лучше. Вес тропинки учитывает **кто** топтал:
  `generator{algo, version}`, агент, человек — разные источники, разные priors.
- Нехоженое чаще не хожено, потому что плохо (survivorship наоборот), а не
  потому что никто не пробовал. Бонус за исследование — ставка, не обещание.
- Самоподкрепление: выигрыш по тропинке делает её ещё более протоптанной.
  Поэтому β > 0 всегда, и библиотека ситуаций хранит распределение, а не
  только лучший путь.

## 11. Качество исполнения и единая валидация (v0.6)

### 11.1 Качество исполнения измеримо отдельно от исхода

Функциональный исход (сертификация, respin) и качество исполнения (читаемость
схемы, полнота BOM, наличие моделей) — разные величины; граф считает обе.

| Величина | Как считается |
|---|---|
| **Полнота входов** | покрытие derived: доля валидаторов/критериев, которые не смогли вычислиться, с причинами (нет SPICE-модели → импедансный критерий невычислим → `Join` без критерия) |
| **Стоимость понимания** | время и число операций от открытия состояния до следующего решения; откаты; `stale`/`blocked`; доля решений человека без вычислимого критерия. **Агент как прибор**: стоимость агента ответить «что делает этот нет и почему так разведён» по одному состоянию — воспроизводимая метрика читаемости |
| **Отложенная цена** | цепочка `Cause` от `Outcome` назад: решение без модели → `Join` без критерия → respin. Технический долг с размерностью |
| **Переиспользуемость** | попадания в библиотеку ситуаций (§10.2): полный канон публикует переносимые тропинки, тяп-ляп не канонизируется |

**Процессный профиль** (по аналогии с профилями нетов): хобби / промышленный /
сертифицируемый задаёт, какая полнота входов обязательна на каком gate. Тяп-ляп
— дефект только там, где профиль его запрещает.

**Гудхарт**: измеряется не наличие модели, а вычислился ли derived, сработал ли
критерий и коррелирует ли с `Outcome`. Модель-заглушка даёт вычислимый, но
неверный критерий — всплывает в credit assignment (§10.3).

### 11.2 Валидация едина по доменам

DRC — не особый механизм, а валидатор домена `layout`. Для любого домена:

```
validate(object, rules, profile) → derived-предикат
```

Домены: schematic, layout, footprint, 3D-model, SPICE/IBIS-model, BOM, docs,
mechanical. У каждого — идентичность, канон (§8), derived-валидаторы и строки в
эффективной таблице ограничений (§8.2). Профиль задаёт обязательные валидаторы
на этап.

Тройка identity / constraints / metrics (§8.5) применяется к моделям без
изменений. 3D-модель компонента:

| | |
|---|---|
| identity | геометрия на сетке, позиции выводов, материалы (если от них есть derived: thermal, масса, DFM) |
| constraints | выводы ↔ пады футпринта; корпус в допусках datasheet |
| metrics | полигоны, точность относительно измерений |

Текстуры — презентация (L1), пока рендер не deliverable; тогда профиль
переводит их в identity — так же, как RF переводит геометрию трассы (§8.5).

**Кросс-доменная согласованность** — derived-рёбра между доменами, проверяемые
обычными валидаторами:

```
пины символа ↔ пады футпринта ↔ выводы 3D ↔ порты SPICE ↔ строка BOM ↔ datasheet
```

Лишний пад или другой порядок портов ловится тем же механизмом, что clearance.

**Сертификация** — валидатор с внешним свидетельством: предикат не вычисляется,
а приходит как `Outcome{evidence: протокол испытаний}` (§10.3). Тот же тип
узла, другой источник истины.

## 12. Запуск: сегментный распределённый PLL (v0.7)

Модель гоняется автоматически по процессам и профилям, веса уточняются по мере
поступления данных, сегменты захватываются каскадом. Отображение на PLL —
рабочее, не метафорическое: у каждого элемента петли здесь есть конкретный смысл.

### 12.1 Отображение

| PLL | Здесь |
|---|---|
| Опорный сигнал | оракул: симулятор → открытые проекты → `Outcome` из поля |
| Генератор | модель с весами (политики Join, priors библиотеки ситуаций, профили) |
| Детектор фазы | расхождение предсказания (путь / исход) и оракула |
| Петлевой фильтр | скорость адаптации весов, забывание |
| Детектор захвата | дисперсия ошибки < порога на N образцах, с гистерезисом; **по `Outcome`, не по прокси** |
| Полоса захвата | насколько далёкую от истины начальную модель петля ещё дотягивает |
| Сегмент | петля на `situation_key × профиль` |
| Распределённость | образцы от многих проектов; агрегируются веса, не платы |

### 12.2 Стадии = стадии захвата

| Стадия | Опора | Что проверяется |
|---|---|---|
| 0. Симулированные оракулы | чистый сигнал с известной истиной | петля способна захватиться; время захвата; полоса |
| 1. Открытые проекты из разных систем | несколько опор с разными смещениями (Altium / KiCad / Eagle — разные конвенции) | кросс-сверка декоррелирует инструментальную ошибку; intent выводится из результата (F22) на настоящих данных |
| 2. Поле (adoption) | реальный шум и дрейф; `Outcome` с задержкой | захват промышленных профилей; удержание; потеря и повторный захват |

Ограничение стадии 1: открытые проекты — выжившие и преимущественно хобби.
Промышленные профили захватываются только на стадии 2. Незахваченный
промышленный сегмент на стадии 1 — не «модель неверна», а «нет опоры».

### 12.3 Каскад захвата

Возникает из факторизации (§8.6, F23): пока сегмент не захвачен, его шум
протекает в связанные веера через пространственные footprints. Захват одного
сегмента снижает шум соседей. Порядок каскада предсказуем: частые и слабо
связанные сегменты — первыми. Без факторизации каскада нет — одна петля с
большой полосой шума; это проверяется абляцией F23.

### 12.4 Три причины «не захватывается»

| Причина | Признак | Лечение |
|---|---|---|
| Модель неверна (канон, профиль) | систематическая ошибка, не падает с объёмом | правка модели |
| Оракул шумный / мало данных | несмещённая ошибка, дисперсия падает с объёмом | ждать или другой оракул |
| Сегмент мультимодален (две школы) | петля болтается между двумя захватами | **разделить сегмент**: сегментация адаптивна, принадлежность ситуации к сегменту — мягкий вес, сходится вместе с остальными («применимость пулов — тоже веса») |

Различение трёх причин — часть метода, не ручная диагностика.

### 12.5 Отказы петли

- **Ложный захват на гармонике** = захват на прокси-метрику (DRC-чисто,
  красиво по skew), не на `Outcome`. Детектор захвата обязан использовать
  отложенный исход (§10.3) — иначе петля уверенно замирает на прокси.
- **Потеря захвата** — новая технология фабрики, новый класс компонентов:
  опора ушла. Нужны детектор потери захвата и повторный захват с расширенной
  полосой. Петля, не умеющая расцепиться, — замороженная модель.
- **Дребезг** на границе захвата — гистерезис в детекторе.

## 13. Агенты и двухскоростная петля (v0.8)

Когда проектируют агенты, скорость итераций растёт на порядки — но только в
части петли, не замкнутой через физику.

### 13.1 Что ускоряется, что нет

| Элемент петли | С агентами |
|---|---|
| Генератор (операции, веера) | машинная скорость |
| Прокси-детектор (DRC, метрики, симуляции) | машинная скорость; дорогие солверы доступны на каждом Join |
| Опора `Outcome` (фабрика, монтаж, EMC, поле) | **фиксированная задержка**; сжимается пропускная способность (параллельные платы), не латентность |

PLL с большой задержкой в обратной связи не может иметь широкую полосу:
подстройка быстрее прихода опоры — автоколебания, не захват.

### 13.2 Риск: прокси-данные затапливают Outcome

Соотношение прокси-образцов к Outcome-образцам взлетает на порядки — условие
ложного захвата (§12.5): быстрая петля с огромной статистикой замирает на
«красиво по DRC» раньше, чем медленная успевает это опровергнуть.

**Двухскоростная петля** (каскадное регулирование): внутренняя быстрая петля
работает на прокси; внешняя медленная **калибрует прокси по Outcome** и
удерживает внутреннюю от захвата на то, что внешняя опровергнет. Достоверность
каждого прокси — вес, сходящийся по Outcome; прокси обучаемые.

### 13.3 Что агенты усиливают в неприятную сторону

- **Тропинки топчут агенты.** Вес источника (F36) становится критическим;
  без него библиотека ситуаций — следы одного роутера, и β приходится держать
  выше, чтобы не захватиться на его смещение.
- «От идеи до выпуска за минуты» — до *проекта*, не до платы. Разница — ровно
  задержка опоры, вокруг которой строится петля.

### 13.4 Стратегическое следствие

Когда рисует агент, ценность инструмента смещается из редактирования в
**валидацию и память**: канон, derived, Outcome-проводка, библиотека ситуаций.
В агентном мире EDA-система — оракул и история, а не редактор.

## 14. Волны: миграция узкого места по конвейеру (v0.9)

Когда проектирование становится дешёвой рутиной, узкое место мигрирует (теория
ограничений): проектирование → фабрика и монтаж → тесты и измерения → полевая
надёжность → цепочка поставок и регуляторика → согласования людьми. Каждая
волна сжимает очередной сегмент; последний сжимается хуже всего.

### 14.1 Физический конвейер — домены графа с первого дня

Фабрика, монтаж, тест, поле — домены с операциями класса X (временные метки,
стоимость, профили) и `Outcome` со свидетельством. Тогда к приходу волны
инструмент измерения уже стоит: **критический путь** от идеи до поля считается
по `Cause`-цепочке тем же механизмом, что blame по треку. Граф показывает, где
сейчас время, раньше, чем это станет очевидно. Без этого каждую волну встречает
новый прибор.

### 14.2 Тесты = проектирование опорного сигнала

Измерения — опора петли (§12.1); выбор измерений — проектирование опоры. План
испытаний — `Fan`/`Join` с критерием **ценности информации**: какие измерения
сильнее снижают неопределённость в незахваченных сегментах. Детектор захвата
знает, где дисперсия велика → знает, какой тест нужен. Оптимальное планирование
эксперимента из того же графа; тест — активное обучение, а не чеклист.

### 14.3 Обратная связь в проектирование

Когда стоимость теста и монтажа известна по сегментам, DFT/DFM — derived-критерии
на Join во время разводки с настоящими весами, а не эвристики. Волна, дошедшая
до теста, возвращается в проектирование числами.
